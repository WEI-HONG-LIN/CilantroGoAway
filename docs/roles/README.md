# 角色分工總覽

每份角色文件都寫成**可以直接當 prompt 使用**的格式：把整份文件（連同 `00_共同規範.md`）貼給 AI 代理，或交給負責的組員，就能照著執行。

## 如何使用

1. 先讀 [`00_共同規範.md`](00_共同規範.md)：所有角色都必須遵守。
2. 再讀自己的角色文件。
3. 單一事實來源（Single Source of Truth）：
   - 玩法規則 → `香菜退散_Godot遊戲企劃書.md`（由遊戲企劃維護）
   - 未決事項 → `docs/企劃分析與待確認事項.md`
   - 決策紀錄 → `docs/decisions.md`（由製作人維護，第一次有決策時建立）

## 角色清單

| # | 角色 | 檔案 | 一句話職責 | 主要交付物 |
|---|---|---|---|---|
| 01 | 製作人／專案管理 | [01_製作人.md](01_製作人.md) | 控制範圍、時程與決策 | 里程碑看板、決策紀錄、週報 |
| 02 | 遊戲企劃 | [02_遊戲企劃.md](02_遊戲企劃.md) | 定義規則，讓規則可以實作、可以驗證 | 企劃書修訂、系統規格、評分數值 |
| 03 | 關卡設計 | [03_關卡設計.md](03_關卡設計.md) | 把規則變成 6 個有節奏的關卡 | `LevelData` 資源、香菜配置表 |
| 04 | 3D 美術（畫面設計） | [04_3D美術.md](04_3D美術.md) | 可愛又一眼可辨的料理與香菜 | 模型、材質、燈光、動畫 |

## 開發流程與交接

```text
          ┌────────── 01 製作人：範圍／時程／決策 ──────────┐
          ▼                                              │
   02 遊戲企劃 ──規格──▶ 06 遊戲邏輯程式 ◀──資源── 04 3D美術
      │                      ▲   ▲                    ▲
      │規則                  │   │                    │
      ▼                      │   │UI場景              │視覺需求
   03 關卡設計 ──LevelData───┘   └── 05 UI/UX ◀──────┘
                                     ▲
                       07 音效 ──────┘（音效事件掛在訊號上）
                                     │
          08 測試遊玩 ◀──每週可玩版本──┘ ──Bug／試玩報告──▶ 01／02／06
```

| 里程碑 | 主導角色 | 主要協作 | 進入下一階段的條件 |
|---|---|---|---|
| M1 操作原型 | 06 程式 | 02 企劃、05 UI/UX | QA 確認灰盒能選取、拿起、旋轉、放回 |
| M2 核心循環 | 06 程式 | 02 企劃、03 關卡 | 一道料理可以完整清除，計數正確 |
| M3 關卡與 UI | 03 關卡、05 UI/UX | 06 程式 | 6 關從開始到結算都能玩完 |
| M4 美術與打磨 | 04 美術、07 音效 | 06 程式、05 UI/UX | 灰盒資產全部替換，回饋完整 |
| M5 測試與交付 | 08 QA | 全員 | 附錄 A 完成定義全部打勾，沒有 P0／P1 bug |
